# Taller Claude Code Plugin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner can use Taller from inside a Claude Code chat — `/taller:new`, `/taller:approve`, `/taller:reject`, `/taller:resume`, `/taller:status`, `/taller:amend`, `/taller:onboard` — and a chat opened in one of her projects starts out knowing it is a Taller project.

**Architecture:** The plugin is a remote control, not a second engine (the owner's choice, 2026-09-28: "Option 1"). Each slash command is a markdown file telling the chat which `taller` command to run and how to talk to the owner around it; `src/taller` stays the single implementation (§3.5). Four library changes make that possible: every question Taller asks can be answered from a file, and a missing answer ends the command with a clear "needs this answer" report instead of waiting on a keyboard; a `taller amend` command; a `taller hook session-start` command the plugin's hook calls; and spend a chat spent on a ticket's branch, read from Claude Code's transcripts.

**Tech Stack:** Python 3.11, the existing `taller` CLI, Claude Code plugin files (`.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `commands/*.md`, `hooks/hooks.json`). No new dependency.

**Spec:** [2026-09-26-taller-design.md](../specs/2026-09-26-taller-design.md) — §3.5 (command surface, naming), §3.1 (the `SessionStart` briefing), §4.6 and §9.8 (amend refreshes every affected project and reports them), §7.5 (the transcript fallback), §8.4 (resume), §10.1 (plugin layout), §15.6 (the ignorance test covers the plugin).

**Builds on:** Phases A, D, B, C on `phase-a/foundations`. Conventions hold: TDD, plain-language messages, UTF-8 at every subprocess boundary, the stub `claude` in every test, never the real `claude`.

## Global Constraints

- The slash-command set is exactly `/taller:new`, `/taller:approve`, `/taller:reject`, `/taller:resume`, `/taller:amend`, `/taller:status`, `/taller:onboard` (§3.5). `/taller:new` creates a **ticket**, never a project.
- A plugin named `taller` with `commands/new.md` is invoked as `/taller:new`: command files are named by the verb alone (`new.md`, not `taller-new.md`).
- Command frontmatter: `description`, `argument-hint`, `allowed-tools`. `allowed-tools` lists only `Bash(taller <verb>:*)` specifiers the command needs — never bare `Bash`.
- The plugin and the catalogue ship knowing nothing about the owner (§15.6, G9): English only, no brand, no project name, no language default. The existing ignorance test scans every tracked file, so it covers the plugin automatically.
- The hook never breaks a session: any error → exit 0 with no output.
- Nothing here spawns `claude` except through `inference.infer` (§3.6).

## Review Focus

1. **A command run from a chat that would ask a question** — the chat has no keyboard for it. Taller must stop with "needs an answer to <id>: <question>", exit with a distinct code, and never hang or silently cancel. *Pinned in Task 1.*
2. **Running the same command again after supplying the answer** — must not duplicate what the first attempt already did (a second ticket, a second onboarding). *Pinned in Task 1.*
3. **A `ticket run` that takes many minutes inside a chat** — the chat's shell times out long before. Commands must start it in the background and report when it finishes. *Pinned in Task 5.*
4. **A hook that cannot work** (Taller not installed in that Python, a broken registry, not a Taller project, garbage on stdin) — the chat starts normally with nothing injected. *Pinned in Task 3.*
5. **Transcript records that would be counted twice** — one message split over several lines, and the transcripts of Taller's own `claude -p` dispatches, whose usage is already in `status.yml`. *Pinned in Task 4.*

### Task 1: Every question can be answered from a file

**Files:** Modify `src/taller/prompter.py`, `src/taller/cli.py`, `src/taller/commands/ticket.py`. Create `tests/unit/test_answers.py`.

**Interfaces — produces:**

```python
class NeedsAnswer(TallerError):          # prompter.py
    qid: str; prompt: str
class AnswerSheetPrompter(Prompter):
    interactive = False
    def __init__(self, answers: Mapping[str, str | list[str]]): ...
# Prompter gains `interactive: bool` (TerminalPrompter True, ScriptedPrompter True)
EXIT_NEEDS_ANSWER = 3                     # cli.py
```

`AnswerSheetPrompter.say` prints (like the terminal); `ask`/`ask_lines` take the next answer for that id (a string for `ask`, a list for `ask_lines`; a tuple-free sheet — each id answers once) and raise `NeedsAnswer` when the sheet has none. `cli.main` gains a global `--answers FILE` (JSON object). When no prompter is passed: `--answers` given, **or stdin is not a terminal** → `AnswerSheetPrompter` (empty sheet without `--answers`); else `TerminalPrompter`. `NeedsAnswer` is caught in `main` and printed as exactly:

```
NEEDS <qid>
<the question text as Taller would have asked it>
Put the answer in the answers file as "<qid>": ... and run the same command again.
```

then `EXIT_NEEDS_ANSWER`. An invalid answer: the existing validation says why, asks the same id again, and the sheet has nothing more for it → `NEEDS` for that id, after the validation message. `ticket new` when the chief cannot classify and `not prompter.interactive`: no fallback questions — the ticket stays `named_by: None` (the chief classifies it again at ① when it runs) and the output says so.

### Task 2: `taller amend`

**Files:** Create `src/taller/commands/amend.py`, `tests/unit/test_amend.py`. Modify `src/taller/cli.py`.

**Interfaces:** `taller amend --reason TEXT [--path PROJECT]`; `amend.run(args, prompter) -> int`.

Behaviour (§4.6, §9.8): commits whatever rule changes are pending and refreshes everything they reach, then reports it.
- **Hub:** `git status --porcelain` in the hub, limited to `modules/`, `brands/`, `profiles/`, `taller.yml`. Pending → `hub.commit(f"amend: {reason}")`; then `generated.refresh_affected(...)`: `module=<id>` per changed `modules/<id>.md`, `brand=<slug>` per changed `brands/<slug>/…`, `everything=True` when a profile or `taller.yml` changed. Report one line per refreshed project with its sync state.
- **Project** (`--path`, or the project the owner is standing in, if registered and adopted): changed files under `.taller/constitution/` except the generated `00-index.md`. Pending → refused unless the checkout is on `main` (`gitio.require_clean_main` does not fit: the change *is* the dirt; check the branch and that nothing outside `.taller/constitution/` is staged); commit those paths `amend: {reason}`, then `generated.refresh(project)`.
- Nothing pending anywhere → "Nothing to amend: change a rule file first." exit 0. An empty `--reason` → `NEEDS amend.reason` through the prompter (Task 1).

- [ ] **Step 1: Failing tests** — `test_amending_a_hub_module_refreshes_every_project_that_uses_it` (two flask projects; edit `modules/never.md` in the hub; `taller amend --reason "No inline styles"` → the hub's last commit subject is `amend: No inline styles`; both projects' `resolved.json` on `main` record the new `hub_sha`; output names both); `test_amending_a_project_slice_commits_it_and_refreshes_that_project`; `test_a_project_amend_off_main_is_refused`; `test_nothing_pending_says_so`; `test_the_reason_is_required`.

### Task 3: `taller hook session-start`

**Files:** Create `src/taller/commands/hook.py`, `tests/unit/test_hook.py`. Modify `src/taller/cli.py`.

**Interfaces:** `taller hook session-start` reads the hook's JSON from stdin (`cwd`); `hook.briefing(cwd: Path) -> str` (pure enough to test; `""` when not a project).

Output (plain text on stdout, which Claude Code adds to the chat's context — §3.1): when `cwd` is inside a registered, adopted project: one line naming the project and its profile; the project's `00-index.md` from `main` (`tickets.read_main`); open tickets, one line each (`0007 · ⑤ gates · blocked: …`); one line pointing at `/taller:status` and `/taller:new`. Capped at `BRIEFING_MAX = 4000` characters (§3.1's ~500-token briefing plus the ticket list). Not a project, or **any** exception (bad JSON, missing registry, git failure) → no output, exit 0.

### Task 4: Spend a chat put into a ticket, from the transcripts (§7.5)

**Files:** Modify `src/taller/spend.py`, `src/taller/commands/ticket.py`. Create `tests/unit/test_transcript_spend.py`, `tests/fixtures/transcripts/*.jsonl`.

**Interfaces:**

```python
def fold(...)                          # also appends result.session_id to spend["sessions"]
def transcript_slug(path: Path) -> str # every non-alphanumeric character -> "-"
def from_transcripts(project: Path, ticket: Mapping, *, root: Path | None = None
                     ) -> dict[str, dict[str, int]]   # by model, UsageRecord field names
```

`from_transcripts` reads `root` (default `~/.claude/projects`) `/<slug>/*.jsonl` for the slug of the project checkout **and** of the ticket's worktree; keeps `type == "assistant"` records whose `gitBranch` is the ticket's branch and whose `sessionId` is not in `spend["sessions"]` (Taller's own dispatches, already counted); counts each `message.id` once (Claude Code writes one line per content block, each repeating the usage); maps `input_tokens`/`cache_creation_input_tokens`/`cache_read_input_tokens`/`output_tokens` to `input`/`cache_write`/`cache_read`/`output`; skips an unparseable line. Not written to `status.yml`; `ticket show` prints `In a chat: <weighted> weighted tokens (not dispatched by Taller)` when non-zero. Records before the branch existed are not attributed (§7.5's time window is for a session-driven ticket, which Option 1 does not have).

### Task 5: The plugin

**Files:** Create `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `commands/*.md` (7), `hooks/hooks.json`, `docs/plugin.md`, `tests/unit/test_plugin_files.py`.

- `plugin.json`: `{"name": "taller", "description": …, "version": <pyproject version>}`.
- `marketplace.json`: `{"name": "taller", "owner": {"name": "Taller"}, "plugins": [{"name": "taller", "source": "./", "description": …}]}` — installable with `claude plugin marketplace add <repo>` then `claude plugin install taller@taller`.
- `hooks.json`: `SessionStart`, matcher `startup|resume|clear|compact`, one command hook `taller hook session-start`.
- Each command file tells the chat, in plain steps: which `taller` command to run (always with `--answers <a file in the session's scratch space>`); on `NEEDS <id>` (exit 3), ask the owner that question in the chat in plain words, add the answer to the file, run the same command again; relay Taller's output in a few plain sentences. `new`, `approve`, `resume` then run `taller ticket run <id>` **in the background** and report when it finishes (Review Focus 3). `reject` asks for the reason in the chat when it was not given. `status` runs `ticket list`, or `ticket show <id>` with an id. `amend` talks the change through, edits the rule file (hub `modules/…`/`brands/…` under `~/.taller`, or the project's `.taller/constitution/…`), then runs `taller amend --reason`. `onboard` runs `taller setup` when the hub is unset (`taller doctor` says so), then `taller project new <name>` or `taller project adopt <path>`.
- `docs/plugin.md`: install, the seven commands, and that work still runs on Taller's own team (Option 1).

- [ ] **Step 1: Failing tests** — `test_the_manifest_names_the_plugin_taller`; `test_the_marketplace_installs_it_from_this_repository`; `test_exactly_the_seven_commands_exist_named_by_verb`; `test_each_command_has_frontmatter_and_only_taller_bash` (every `allowed-tools` entry matches `^Bash\(taller [a-z -]+:\*\)$`); `test_each_command_runs_its_own_taller_verb` (e.g. `reject.md` contains `taller ticket reject`); `test_long_runs_go_to_the_background` (`new`, `approve`, `resume` mention `background`); `test_every_command_handles_needs` (each mentions `NEEDS` and `--answers`); `test_the_hook_calls_the_cli`.
